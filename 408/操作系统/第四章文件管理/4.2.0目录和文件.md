# 文件控制块（FCB）

文件控制块是用来存放文件各种信息的数据结构，一个文件对应一个 FCB。

**文件目录**：所有 FCB 的集合构成文件目录。
就是一个目录下的所有FCB


## FCB 结构

| 分类 | 字段 | 描述 |
|------|------|------|
| 基本信息 | 文件名 | 文件的标识名称 |
| 基本信息 | 类型 | 文件的类型分类 |
| 基本信息 | 文件大小 | 文件所占存储空间大小 |
| 基本信息 | 文件数据块指针 | 指向文件实际数据存储位置的指针 |
| 存取控制信息 | 文件权限 | 文件的访问权限控制（如读、写） |
| 使用信息 | — | 文件使用相关的元数据 |
# 索引节点
UNIX系统使用了文件名和描述信息分离的设计策略
**将文件的描述信息独立组织为索引节点**
目录项仅由文件名及其对应的索引节点号构成

FCB只存名字和索引编号
索引节点存所有的描述信息
例如
1. 类型
2. 大小
3. ...
4. 磁盘块 6 1 4：文件内容

## 索引节点的两种形态

为兼顾持久存储与高效访问，文件系统将索引节点设计为两种形态：

### 磁盘索引节点

存储于磁盘上，作为文件的永久档案，每个文件有唯一磁盘索引节点：

| 字段     | 描述                             |
| ------ | ------------------------------ |
| 文件主标识符 | 标识文件所属的用户或用户组                  |
| 文件类型   | 普通文件、目录文件或特殊文件                 |
| 文件存取权限 | 规定文件主、核准用户及一般用户的访问权限           |
| 文件物理地址 | 通过 13 个地址项以直接或间接方式记录数据所在盘块编号   |
| 文件长度   | 以字节为单位表示文件的实际大小                |
| 文件链接计数 | 统计指向该文件的目录项（**硬链接**）数量         |
| 文件存取时间 | 记录文件最近被访问、修改的时间，以及索引节点最近被修改的时间 |

### 内存索引节点

文件被打开时，磁盘索引节点载入内存并附加运行时状态信息：

| 字段 | 描述 |
|------|------|
| 索引节点号 | 在内存中唯一标识该节点 |
| 状态 | 指示节点是否被上锁或已修改，便于缓存一致性管理 |
| 访问计数 | 进程每访问一次加 1，访问结束减 1，判断节点是否可释放 |
| 逻辑设备号 | 标识文件所属文件系统的逻辑设备号 |
| 链接指针 | 分别指向空闲链表与散列队列，便于内核高效调度和回收 |

# 目录结构

## 单级目录结构

整个文件系统只维护一张目录表，所有文件条目都在同一级。

| 维度  | 说明                                   |
| --- | ------------------------------------ |
| 结构  | 线性表，所有文件平铺在同一目录下                     |
| 优点  | 实现简单                                 |
| 缺点  | 命名冲突（不允许重名）；查找效率低（需遍历整张表）；不便于文件共享与保护 |
| 适用  | 早期单用户操作系统                            |

## 两级目录结构

将目录分为**主文件目录（MFD）**和**用户文件目录（UFD）**两级，每个用户拥有独立的 UFD。

| 维度  | 说明                                     |
| --- | -------------------------------------- |
| 结构  | MFD 记录用户名及对应 UFD 指针 → 各用户 UFD 独立管理自身文件 |
| 优点  | **解决命名冲突**（不同用户可有同名文件）；隔离性好；查找限定在用户目录内 |
| 缺点  | 缺乏灵活性，用户间不便于共享文件；无法进一步分类               |
| 适用  | 多用户系统早期阶段                              |

## 树形目录结构

在两级目录基础上扩展为任意层级，形成倒置的树状结构，现代操作系统普遍采用。

| 维度  | 说明                                         |
| --- | ------------------------------------------ |
| 结构  | 根目录为起点，向下逐级分支，文件为叶节点                       |
| 优点  | 层次清晰，便于分类组织；彻底解决命名冲突（不同路径下可同名）；方便文件共享与权限控制 |
| 缺点  | 查找文件需沿路径逐级访问，多次 I/O；目录管理复杂度较高              |
| 路径  | **绝对路径**（从根目录出发）和**相对路径**（从当前目录出发）         |

## 无环图目录结构

树形目录结构便于文件分类，但难以支持文件共享。在其基础上引入指向同一节点的有向边，使目录结构演变为有向无环图。

| 维度  | 说明                             |
| --- | ------------------------------ |
| 结构  | 在树形目录基础上增加有向边，允许多个目录指向同一文件或子目录 |
| 优点  | 方便文件分类且支持灵活的文件共享               |
| 缺点  | 删除操作复杂，需额外的共享计数器管理开销           |

**删除策略**：系统为每个共享节点维护共享计数器——新增共享链时 +1，删除请求时 -1，仅当计数器归零才真正删除节点。
# 文件的共享
## 硬链接（基于索引节点的共享方式）

基于索引节点的共享机制——多个目录项指向同一个索引节点，就是同一份文件。

![](Pasted%20image%2020260618154223.png)

**它在干什么**：让同一个文件可以出现在文件系统的多个位置，不同路径下都能访问到同一份数据，实现文件共享。比如 `/home/user/a.txt` 和 `/backup/a.txt` 指向的是同一个文件，改一个另一个也变。

**原理**：UNIX 把文件名和文件描述信息（inode）分开了。目录项里只存两样东西：文件名 + inode 号。真正的文件属性、数据块指针全在 inode 里。硬链接就是让两个不同的目录项，存同一个 inode 号，这样它们就指向同一个文件了。

**链接计数**：inode 里专门有个字段记录"有几个目录项指向我"。每创建一个硬链接（即新增一个目录项指向这个 inode），计数 +1。每删除一个目录项，计数 -1。只有计数归零了，说明没人再引用这个文件了，系统才真正把文件数据和 inode 都回收掉。这就是为什么硬链接删除时不会误删共享文件——删的只是一个目录项，只要还有其他目录项指着 inode，文件就还在。

**限制**：硬链接不能跨文件系统——因为 inode 号只在单个文件系统内唯一，换到另一个文件系统，inode 号就对不上了。也不能链接目录——如果给目录创建硬链接，目录树下就会出现环路，比如 `dirA → dirB → dirA`，遍历文件系统时就会死循环。


## 软链接（符号链接）

快捷方式。B 想要共享 A 的文件，系统会创建一个新的 Link 文件 L，L 里面只存目标文件的路径名。

![](Pasted%20image%2020260618155824.png)

他的引用计数不会改变，但是删除源文件后会找不到路径而失效



**它在干什么**：本质就是给文件建一个"快捷方式"。比如 A 有一个文件 `/data/report.pdf`，B 在自家目录下 `ln -s /data/report.pdf ~/我的报告.pdf`，B 访问 `~/我的报告.pdf` 时，系统发现这是个软链接，读到里面存的路径 `/data/report.pdf`，自动跳过去访问真正的文件。

**原理**：软链接本身是一个独立的小文件，有自己的 inode 和数据块。它的数据块里不存文件内容，只存目标文件的路径字符串。访问软链接时，操作系统发现它的文件类型标记是"符号链接"，就读取里面的路径，再根据路径去找到真正的目标文件。这个过程叫路径解析，相当于多绕了一步。

**优点**：可以跨文件系统，因为软链接存的是路径字符串，inode 号不用对上。可以链接目录，不会产生环路——软链接和目标是两个独立 inode，系统遍历时能识别并选择是否跟随。

**缺点**：原文件被删除或移动后，软链接就断链了，路径失效变成死链接。每次访问多一次路径解析，有一点点额外开销。

**与硬链接的关键区别**：硬链接是同一个 inode 挂了多个名字，删一个不影响其他的。软链接是一个独立文件里写了目标地址，目标没了链接就废了。打个比方——硬链接像同一个人有多个身份证，软链接像路牌上写了"往前 200 米左转"。

### 访问控制
基于用户身份进行权限管理

最常用的方法是给每个文件和目录附加一个**访问控制列表（ACL）**，明确指定各用户名及其允许的访问类型。优点是灵活，支持复杂访问策略；缺点是列表长度不可预知，空间管理开销大。现代系统常采用精简 ACL 来缓解。

精简 ACL 将用户划分为三类：

- **拥有者**：创建文件的用户。
- **组**：一组需要共享该文件且具有相似访问需求的用户。
- **其他**：系统中除拥有者和同组用户外的所有用户。

每种访问类型用一个二进制位表示，只需一个 3×4 位的矩阵即可描述三类用户的全部权限。文件创建时，系统将拥有者的用户名及其所属组名记录在 FCB 中。用户访问文件时，按优先级匹配：若为拥有者 → 授予拥有者权限；若同组 → 授予组权限；否则 → 授予其他用户权限。
